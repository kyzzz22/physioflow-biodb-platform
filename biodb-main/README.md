# BioDBserver

## 動機

そもそもこのサーバは菅谷研究室における．生体情報処理の技術の統合と集約を目的としている研究の一環として制作されている．

emopyが既存コード資産の統合だとすれば，BioDBはデータ資産の統合が主たる目的に設計されている．

その性格上，BioDBは生データの保管のためのAPI，それに付随する最低限のユーザ機構のみを持ちます．

これのガワとなるアプリを作ることで研究生活が捗ることでしょう．ある意味ではemopyはガワとなるアプリではあります．

## 概要

### 使用したDB

以下の表の通りである．各情報を本当にこのDBで管理していいか，他のDBを使えるかはさらなる検討が求められる

| DB | 使用目的 | 採用理由 |
| -- | -- | -- |
| ~~InfluxDB~~ | ~~生体情報の保存~~ | ~~生体センサ情報は基本的には時系列データであり，高速な読み書きが求められるため，時系列データに特化した時系列DBを用いることにした．その中でInfluxDBはオープンソースで使えるため，使用．~~ |
| victoria metrics | 生体情報の保存 | 生体センサ情報は時系列データであり，高速な読み書きが求められるため，時系列DBを用いる．InfluxDBを使用していたが，大量リクエスト時のストールが問題になったため，victoria metricsに移行 |
| MongoDB | 長期トークンの管理，イベント管理 | 特に高速な読み書きが求められることは少ないと判断，スキーマレスで使いやすいため採用．長期トークンとかは割と仕様が定まれば，SQLとか他のDBに移してもいいかも．イベントデータは補足情報を持たせたい場合が多いと思うので，このMongoDB管理でいいと思ってる． |
| PostgresDB | ユーザ情報管理，パーミッション管理 | ユーザ情報やパーミッション管理は厳密に行えた方がいいため，スキーマを定義して厳密にやりやすいRDBを採用．まあ他のDBを採用する理由もないので |

### 機能別ルーティング

各データはDBに保管される．リクエストがあればこれらの情報を参照して，書き込みや読み出しを行う．それぞれの機能のAPIサーバを実装している．それらをnginxを用いてルーティングしている感じ．

| ルーティング | 機能 |
| -- | -- |
| /auth | 認証認可サーバ．トークンの作成管理API，ユーザ情報API，被計測者管理API，JWT発行 |
| /sensor | 生体情報APIサーバ．基本的には読み出しと書き込みしかできない |
| /event | イベントデータ管理API．基本的なCRUDに対応 |

現状の実装では，実験から解析に必要な最低限の機能のみの実装となっている．

## クライアント側で最低限気を付けること

### JWT(Json Web Token)とは

ややこしい説明を省くと，特定のスキーマを持ったJSONオブジェクトをBase64エンコードしたものと秘密鍵の署名のセットにしたトークンです．端的に言えば秘密鍵がなければ，作成検証が不可能となる仕組みで，秘密鍵をサーバだけが知っている状態であればそのトークンは自身が作ったものだと確認できます．

JWTはWebアプリの認証認可フローで見かけることが多いです．実際今回のプロジェクトでも認証認可フローにて使われています．

JWTの中には有効期限の情報が入っており，その時刻を過ぎれば，そのJWTは無効になります．つまりJWTは悪意のある攻撃者に奪われたとしても，有効期限を過ぎれば使えなくなるという点がいい点です．またリクエスト毎に権限範囲をDBに確認する必要がないため，高頻度でデータを送信する生体情報計測と相性もいい感じです．

### 実際に気を付けてほしいこと

このシステムは長期トークンを使用した認証，JWTを使用した認可を採用しています．

基本的にはユーザはユーザIDと長期トークンを使用してJWTを入手します．

また上記の通り，有効期限が短めに設定されているため，定期的にJWTを取得しなおす必要があります．

大抵のAPIはJWTを必要とします．そのことを頭に入れておいてください．特にアプリ作成する人は気を付けた方がいい部分になります．

### 実際の取得フロー

権限毎にトークンの発行するためのエンドポイントが微妙に違います．ここではデータの書き込みに使用できるJWTの取得フローを記述します．

1. "/auth/jwt/sensors/writejwt"に**ユーザID**と**長期トークン**を渡す
2. 取得したJWTをAPIリクエストのAuthoraizationヘッダーに付与
3. JWTの有効期限が切れる前，ないしは有効期限を過ぎた場合はエラーが出るので，そのタイミングで再取得

#### 1について

生体情報を扱う場合はライブラリの豊富さからPythonを使用する場合が多いのでサンプルスクリプトもPythonで記述します．他の言語から使用したい場合は，適宜読み替えていただけると助かります．

研究室のコード資産をまとめたemopyからアクセスする場合は，そちらのドキュメントに使用方法を書いてありますので，そちらを参照してください．

**リクエスト例**

```python
import requests

SERVER_URL = "server url" # サーバのURL
USER_ID = "your user id"
TOKEN = "your token"
PARTICIPANT_ID = "participant id"
START_TIME = datetime(2025, 1, 1, 0, 0, 0) # サンプルの時間
END_TIME = datetime(2025, 1, 1, 0, 1, 0) # サンプルの時間

body = {
    "user_id": USER_ID,
    "token": TOKEN,
    "participant_id": PARTICIPANT_ID,
    "start_time": START_TIME.isoformat(),
    "end_time": END_TIME.isoformat()
}
response = requests.post(f"{SERVER_URL}/auth/jwt/sensors/writejwt", json=body)
jwt = response.get_json()["jwt"]
```

この例では，jwtの取得まで行いました．上記スクリプトを実行したとき，有効なトークンであれば，jwtが発行され変数jwtに格納されます．

#### 2について

取得したJWTをAPIリクエストのAuthoraizationヘッダーに付与

```python
body = {} # 本来はリクエストに応じて正しくbodyを設定しなければいけないがここでは省略
response = requests.post(f"{SERVER_URL}/sensor/data/write", json=body, headers={"Authorization": f"Bearer {jwt}"})
```

## セットアップ

リポジトリ直下の `compose.yaml` で、DB・API・WebUI をまとめて起動する。
各サービスは Compose の既定ネットワークで名前解決するため、外部ネットワークの作成は不要である。

1. `.env.example` を `.env` としてコピーし、5つの値を設定する。

   ```bash
   cp .env.example .env
   ```

   `.env` に含めるのはアプリケーション鍵と Google OAuth client ID だけである。DB の接続情報は `compose.yaml` に固定している。

2. イメージをビルドして起動する。

   ```bash
   docker compose up --build -d
   ```

   WebUI はビルド済みの静的ファイルとして NGINX に同梱され、`http://localhost:5002/WebUI/` で利用できる。外部に公開されるポートは NGINX のみで、API と DB は Compose 内部からだけ到達できる。

3. 最初の管理者を登録する。Google ログインを受け付けるには、先に対象メールアドレスを DB に登録する必要がある。

   ```bash
   docker compose --profile tools run --rm admin --email user@example.com
   ```

   `admin` は通常のサーバ起動には含まれない one-shot コンテナで、`uv run` により `create_admin.py` だけを実行する。API サーバ本体の依存管理や起動方法は変更していない。

既存データを維持するため、PostgreSQL・MongoDB・VictoriaMetrics のデータは従来と同じリポジトリ配下のディレクトリへ保存する。データを完全に初期化する場合は、停止した状態で各データディレクトリを退避または削除すること。
