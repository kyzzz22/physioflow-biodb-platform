## 1. 業務背景と目標

### 1.1 背景と課題

研究室では行動・生理実験（感情、認知、脳波等）を実施しており、データは複数のシステム・複数の参加者・複数の実験から生成される。現状の課題：

| 課題 | 具体的な症状 |
|---|---|
| データ分散・形式不統一 | 実験データ、センサーデータ、イベントマーカーが各システムとエクスポートファイルに散在し、一元的な管理・再利用ができない |
| 「どの実験、どの参加者か」を区別できない | 時系列 DB に複数のデータ塊が並ぶだけで、実験次元が無く、同一参加者の異なる実験データを区別できない（会議の核心問題） |
| 実験の再現ができない | 実験条件（刺激セット、順序、パラメータ）が人の記憶/メモにのみ存在し、後から再現できない |
| デバイスデータが未統合 | 脳波等の生体デバイスデータに統一された収集→保存の経路が無い |
| 分析/可視化は手作業の搬送 | 外部ツールにエクスポートして初めて分析でき、プラットフォーム内で完結しない |

### 1.2 プラットフォームの目標

**実験のライフサイクル全体をカバーする研究データプラットフォーム**：設計 → 収集 → 保存 → 管理 → 分析 → 可視化。

**ビジョン**：生体実験を「一度収集すればどこでも再利用」——実験定義、生データ、分析結果が同一プラットフォームで完結し、再現可能・共有可能・クロス実験分析可能。

### 1.3 2 つのコンポーネントの位置づけ

| コンポーネント | 位置づけ | 担う役割 |
|---|---|---|
| **PhysioFlow（PF）** | 実験ワークフロー（フロントエンド） | ビジュアルなプロトコル設計、実行、参加者インタラクション、デバイス収集、再現可能なデータパケットのエクスポート |
| **BioDB** | 生体データウェアハウス（バックエンド） | センサ時系列（VictoriaMetrics）、イベント（MongoDB）、ユーザー/権限（PostgreSQL）、JWT 認証 |
| **統合層** | PF 収集 → BioDB 保存 → プラットフォームで管理/分析/可視化 | 「実験ID + 協力者ID」の二段識別で保存 |

**核心原則（会議確認済み）**：PF プロトコル = ドメインモデル（実験条件の唯一の事実源）；BioDB = データウェアハウス（時系列 + イベントのみを保存し、アプリケーションロジックを担わない）。

## 2. ステークホルダーと役割

| 役割 | 主な活動 | 関心事 | プラットフォーム側ビュー |
|---|---|---|---|
| **実験設計者（研究者）** | PF でプロトコルを設計（ノード図/アンケート/認知タスク/条件）、デバイスコネクタを設定、バージョンをフリーズ | 設計が速い、再現可能、参加者体験 | ComposerV2 エディタ、テンプレートライブラリ |
| **実験オペレーター** | セッションを実行、収集を監視、デバイス障害を処理、BioDB へプッシュ | 流れがスムーズ、障害から復旧できる、データが失われない | ランニングページ、BioDB エクスポート |
| **被計測者（協力者）** | 実験を完了（画面操作/アンケート/認知タスク） | 画面が親しみやすい、中断されない | Participant 画面（多言語） |
| **データ分析者** | BioDB からデータ取得、前処理、統計/ML、可視化 | データが完全、識別が明確、追跡可能 | BioDB データ管理パネル、分析/可視化モジュール |
| **管理者** | ユーザー/協力者/長期トークン/データ保持の管理 | セキュリティ、コンプライアンス、制御 | BioDB 管理 UI |

権限モデル（現状 + 目標）：BioDB には「長期トークン → 用途別 JWT（sensor_read/write/event、時間窓 claim）」が既にある；プラットフォーム側の統一権限/監査ビューは P3 項目（D10）。

## 3. 核心業務シナリオ（ユースケース）

### UC-1 実験の設計
研究者がテンプレート（Emotion/SAM、Stroop、Go/No-Go）または空白プロトコルで実験を構築 → 条件/刺激/アンケートを設定 →（任意）デバイスコネクタを設定 → プロトコルをフリーズ（不変、configHash 含む）。
- 前提：ログイン済み、設計権限あり
- 成果物：フリーズされた protocol（`protocolId` = 実験ID）
- PF の既存能力が全てカバー（13+ ノードタイプ、9 問題タイプのアンケート、PPT 式インターフェース編集、i18n zh/ja/en）

### UC-2 実験の実行と収集
オペレーターがセッションを作成 → 参加者が参加 → ノード実行 + 参加者インタラクション +（任意）device sampler が sampleRateHz で収集 → セッション完了。
- 特徴：決定的ランタイム（クロック/ID 注入）、一時停止/再開/リトライ/スキップ、スナップショット復元、イベントリプレイ
- 成果物：ローカルデータパケット（events / responses / device_events JSONL+CSV / BIDS / データ辞書）
- 異常時：断線、デバイス切断、参加者の途中退出 → セッションは復旧可能、データは失われない

### UC-3 データの取り込み（BioDB へのプッシュ）
セッション完了後にプッシュ：時系列 → VictoriaMetrics（タグ：`experiment` + `participant` + `experimenter`）；イベント → MongoDB。
- 識別解決：`experimentId`（プロトコル設定 → `protocolId` フォールバック → settings デフォルト）；`participantId`（プロトコル → settings マッピング → デフォルト）
- セキュリティ：長期トークン → chunk の時間窓で write JWT を発行（8 分ごとリフレッシュ）、`experiment` は JWT claim から注入（書き込み者は偽造不可）
- 障害処理：JWT リフレッシュリトライは実装済み；断線/再送/冪等の完全な戦略は P3（D9）

### UC-4 データ管理（Phase 2、D3）
実験/協力者単位で BioDB データを閲覧、時間帯表示、イベント CRUD、簡易曲線、データ辞書閲覧。
- 受け入れ：D2 でプッシュしたデータがパネルで見え、イベントを管理でき、同一参加者の異なる実験データをそれぞれ読み戻せる

### UC-5 データ分析（Phase 3、D7）
BioDB から読み戻し（experiment+participant でフィルタ）→ 前処理（リサンプリング/フィルタ）→ 特徴（HRV/EDA/スペクトル）→ 統計/ML → 結果のエクスポートまたはイベントへの書き戻し。
- 原則：分析は読み戻し API を消費し、書き込み側に依存しない

### UC-6 可視化（Phase 3、D8）
履歴複数カラムの重ね曲線、リアルタイムモード（ストリーミングプッシュ後）、感情マップ。

### UC-7 プラットフォーム管理（Phase 4、D10）
プラットフォームレベルの役割/権限/監査ビュー、統一認証体験。

## 4. 業務ルール（重要な制約）

| # | ルール | 根拠/実装 |
|---|---|---|
| R1 | **二段識別の一意性**：データは「experiment + participant」で区別；同一 participant の異なる experiment データは混在させない | 会議の核心；D1 で `experiment` タグ追加；読み戻しは JWT scope でフィルタ |
| R2 | **experiment 識別の偽造防止**：`experiment` は JWT 発行側（長期トークン + writejwt）が注入し、書き込みリクエストは直接持たない | `04-d1-experiment-tag.md` の設計決定 |
| R3 | **プロトコルフリーズは不変**：フリーズ後は不変（configHash 含む）、再現性の基盤；条件情報はプロトコルのみ（Excel/条件 DB は導入しない） | 会議決定；PF 既存 |
| R4 | **タイムスタンプ精度**：BioDB はナノ秒；PF イベントは ISO + epoch ms + monotonic の三時計、精度を下げない | 会議決定；現状で充足 |
| R5 | **データの帰属**：experimenter（書き手）と participant（被計測者）の二視点；イベントは created_by（実験者）/user_id（協力者）を記録 | BioDB 既存モデル |
| R6 | **権限の最小化**：長期トークンはプロトコル内に置かない（settings ローカルのみ）；短命 JWT は時間窓付き | Phase 1 既存 |
| R7 | **再現可能なエクスポート**：セッションデータパケット = プロトコル（フリーズ）+ イベント + device_events + BIDS + データ辞書 | PF 既存エクスポート |

## 5. データと識別体系

### 5.1 エンティティ関係

```
protocol（PF、フリーズ済み不変）
  └─ protocolId = 実験ID（ex: exp_nomura_ninomiya）
  └─ protocol.biodb { enabled, experimentId, participantId, experimentLabel? }
  └─ 条件/刺激/アンケート/デバイス設定（ドメインモデル、唯一の事実源）
       │
session（1 回の実行）
  └─ participant（協力者 ID、21 桁 nanoid）
  └─ イベント/レスポンス/device_events（三時計タイムスタンプ）
       │  pushSession でプッシュ
       ▼
BioDB
  ├─ VictoriaMetrics 時系列：series = biodb_<column>、tag = experiment + participant + experimenter、ns タイムスタンプ
  ├─ MongoDB イベント：user_id（協力者）/ created_by（実験者）/ 時刻 / details
  └─ PostgreSQL ユーザー/権限：21 桁 ID、長期トークン、scope
```

### 5.2 識別マッピングチェーン

| 層 | 識別 | 例 |
|---|---|---|
| PF プロトコル | `protocolId` | `exp_nomura_ninomiya` |
| PF プロトコル設定 | `protocol.biodb.experimentId`（空の場合は protocolId でフォールバック） | `exp_nomura_ninomiya` |
| BioDB 時系列タグ | `experiment` | `exp_nomura_ninomiya` |
| BioDB 時系列タグ | `participant`（プロトコル設定 → settings マッピング → デフォルト） | `<21桁 ID>` |
| BioDB 時系列タグ | `experimenter`（= JWT sub） | `<21桁 ID>` |

### 5.3 データ辞書連携（D4）

PF には `graphDataDictionary` が既にある；「時系列チャネルリスト（dataType/unit/sampleRate）→ データ辞書」を連携し、プッシュ/エクスポートに同梱することで、チャネルデータの解釈可能性を保証する。

## 6. プロトタイプ先行計画（会議決定 → 本段階のアクション）

会議の決定：**いきなり要件定義/DB 設計ではなく、まず PF で 5 つ前後のプロトタイプ実験を作成し、そこから要件を抽象化する**（9/1 前後の会議で整理、担当：古久・なべしま・くおわみ、全員が試用）。

### 推奨する 5 つのプロトタイプパターン（3 テンプレート + 空白プロトコルで作成可能）

| # | プロトタイプ | カバーする要件 | 使う PF 能力 |
|---|---|---|---|
| P1 | 感情アンケート型（Emotion/SAM） | 自己評価スケール + メディア刺激；イベントマーカー | アンケート（9 問題タイプ/条件スキップ/スコア）、media ノード |
| P2 | 認知タスク型（Stroop） | RT/正答率、一致条件、練習ブロック | cognitive-task 実行、generateStroopTrials |
| P3 | 抑制タスク型（Go/No-Go） | 見逃し/誤反応、Go 比率、抑制ウィンドウ | cognitive-task 実行、generateGonogoTrials |
| P4 | 複数実験対照型（同一参加者 × 2 実験） | **experiment タグの隔離を検証**：同一 participant の 2 つの異なる実験をそれぞれ読み戻せる | protocol.biodb.experimentId 設定 + pushSession（D1/D2 と連携） |
| P5 | デバイス収集型（シミュレーションコネクタ + センサー） | デバイスデータ収集 → BioDB プッシュ → 読み戻し一致 | device connector、device sampler、BioDB エクスポート（Phase 1 で確立済み） |

### プロトタイプから抽象化する内容（9/1 会議の成果物）

1. 各実験が必要とする**識別とメタデータ**（名称/条件/刺激セット/仮説/IRB 等——どれをプロトコルに、どれを experiment メタデータに入れるか）。
2. 各実験の**データ形態**（チャネル、サンプリングレート、イベントタイプ）→ データ辞書の要件。
3. 参加者視点の**画面とフロー要件** → テンプレート化の機会。
4. **クロス実験分析**に必要な最小限の識別の一貫性。
5. デバイス収集の実際の**品質要件**（フレーム落ち率、タイムスタンプ連続性）。

## 10. リスクとオープンクエスチョン

| リスク/問題 | 影響 | 対策 |
|---|---|---|
| プロトタイプ要件の抽象化と D1/D2 並行開発の衝突 | プロトタイプが新たな識別要件を出す可能性 | 9/1 会議前に D1/D2 を完了（低コスト）、プロトタイプ P4 で隔離効果を直接検証 |
| experiment メタデータ（仮説/IRB/プロトコルスナップショット）の保存先 | 会議で「任意」扱い | まず PF プロトコルで保持；プロトコルスナップショットの BioDB 保存は任意の後続 |
| 実脳波デバイス適応コスト | 高、ハードウェア依存 | シミュレーション経路は検証済み、D5 は単独項目、Phase 2 のクリティカルパス外 |
| クロス実験分析の一貫性 | 実験ごとにチャネル/イベント命名が異なる | データ辞書連携（D4）を先行、プロトタイプ P1-P3 からチャネルリストを抽出 |
| やらないこと | プラットフォームのマルチテナント/クラウドホスティング、任意 JS 注入、自動統計結論生成 | 明確に除外（`03-development.md`） |
